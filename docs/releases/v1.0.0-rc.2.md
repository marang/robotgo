# RobotGo v1.0.0-rc.2

Status: **release candidate**

This second stable-line release candidate re-freezes RobotGo's reviewed public
API after substantial post-`v1.0.0-rc.1` work. Publishing stable directly from
that older candidate would not satisfy RobotGo's frozen-contract rule, so
`rc.2` starts a fresh qualification window without broadening the documented
platform support claims.

## Install

RobotGo requires Go 1.26 or newer. After the candidate is published, install
the independent fork explicitly:

```bash
go get github.com/marang/robotgo@v1.0.0-rc.2
```

Use the fork module path:

```go
import "github.com/marang/robotgo"
```

Do not infer fork releases from local tags fetched from
`go-vgo/robotgo`; verify tags against the authoritative `marang/robotgo`
origin.

## Changes since rc.1

- Added deny-by-default autonomous GUI actions with bounded scroll, drag,
  keyboard chord, activation, cleanup, and typed ownership/error contracts.
- Added policy-gated desktop image observations, bounded in-process OCR and
  geometry-only visual analysis, plus accessibility-first semantic UI
  observations on Linux, Windows, and macOS.
- Added semantic element actions, postconditions, Action Proof, deterministic
  target resolution, target evidence clauses, and single-use capability
  leases.
- Added privacy-tiered RobotGo Trace v1, the payload-free Semantic Recorder and
  Recorded Flow v1, and the advisory Verified Flow Plan v1 capability planner.
- Hardened published release-evidence assets against collisions and stabilized
  the hosted GNOME/KDE evidence fixtures, including a digest-preserving move
  from the expired Daily base-image URL to its direct HTTPS archive-bucket
  path.
- Raised the module's minimum Go version from 1.25 to 1.26.

The full itemized history is in the
[changelog](https://github.com/marang/robotgo/blob/v1.0.0-rc.2/docs/CHANGELOG.md#robotgo-v100-rc2--2026-10-03).

## Compatibility contract

The [Runtime Compatibility Matrix v1](https://github.com/marang/robotgo/blob/v1.0.0-rc.2/docs/compatibility/runtime-v1.md)
remains the release-candidate platform contract. Its
[machine-readable source](https://github.com/marang/robotgo/blob/v1.0.0-rc.2/docs/compatibility/runtime-v1.json)
maps every
`supported` row to exact release-blocking checks. `Implemented / evidence
pending` remains deliberately outside the support claim.

The supported platform scope is unchanged from `rc.1`: bounded native and
Pure-Go Linux/X11 behavior; advertised wlroots/Sway and evidenced Hyprland
behavior; consent-aware GNOME/KDE portal input, capture, and bounds; consent-
free macOS contracts; and native plus bounded Pure-Go Windows behavior.
Permission-granted macOS capture, input, and Accessibility operations remain
implemented/evidence-pending under
[LAB-69](https://linear.app/riotbox/issue/LAB-69/add-permission-granted-self-owned-macos-runtime-evidence).

The checked API manifest is intentionally different from `rc.1`. Consumers of
the agent package should pin `rc.2` and review schema versions instead of
assuming wire compatibility from Go source compatibility alone.

## Migration guidance

Applications upgrading from `rc.1` should:

1. Build with Go 1.26 or newer.
2. Re-generate or revalidate code that persists agent catalog, audit, runtime
   diagnostic, analysis, target, proof, Trace, recorder, or flow-plan schemas.
3. Keep all new image, accessibility, mutation, evidence, Trace, recorder, and
   planning capabilities deny-by-default and explicitly bounded in policy.
4. Treat Action Proof and cleanup-pending results as authoritative; do not
   convert a post-dispatch error into a false success or retry while input
   ownership remains unresolved.
5. Continue to treat portal consent, macOS permissions, and compositor
   capabilities as runtime properties rather than install-time guarantees.

No migration step should persist screenshots, clipboard contents, typed text,
OCR input, window content, native handles, capability tokens, or permission
artifacts. Real-desktop evidence must use disposable, self-owned fixtures and
clean every transient artifact on success, failure, timeout, and cancellation.

## Release evidence

This preparation is not publication evidence. The final merged candidate must
pass a new exact manual Release Evidence run before its annotated tag is
created. Publishing the GitHub prerelease then triggers exact-tag evidence from
`v1.0.0-rc.2` and attaches:

```text
robotgo-release-evidence-v1.0.0-rc.2-<commit>.tar.gz
robotgo-release-evidence-v1.0.0-rc.2-<commit>.tar.gz.sha256
```

Verify the downloaded archive before extracting it:

```bash
sha256sum -c robotgo-release-evidence-v1.0.0-rc.2-*.tar.gz.sha256
```

The release is no-go if either asset is absent, the checksum fails, the bundle
does not identify the annotated tag's peeled commit, any of the six platform
snapshots is missing, or any of the 29 required checks is not successful.

## Qualification and rollback

The stable `v1.0.0` qualification window starts only when GitHub publishes
`v1.0.0-rc.2` and lasts at least seven full calendar days. Until that immutable
timestamp is recorded in the fail-closed preflight, stable publication remains
disabled.

Any unresolved critical/high regression, incompatible public API drift,
supported-platform evidence failure, privacy/cleanup regression, or mismatch
between source, tag, release, evidence bundle, and checksum rejects the
candidate. Published tags are immutable: do not delete or move a rejected tag;
fix the issue and publish a new incremented candidate with fresh evidence.

Consumers can roll back reproducibly with:

```bash
go get github.com/marang/robotgo@v1.0.0-rc.1
```
