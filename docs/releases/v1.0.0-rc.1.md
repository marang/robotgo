# RobotGo v1.0.0-rc.1

Status: **release candidate**

This first stable-line release candidate freezes the reviewed public Go API and
the support scope below. It does not broaden permission- or
compositor-dependent behavior beyond the versioned compatibility contract.

## Install

RobotGo requires Go 1.25 or newer. Install the independent fork explicitly:

```bash
go get github.com/marang/robotgo@v1.0.0-rc.1
```

Use the fork module path:

```go
import "github.com/marang/robotgo"
```

Do not infer fork releases from local tags fetched from
`go-vgo/robotgo`; verify tags against the authoritative `marang/robotgo`
origin.

## Compatibility contract

The [Runtime Compatibility Matrix v1](../compatibility/runtime-v1.md) is the
release-candidate contract. Its
[machine-readable source](../compatibility/runtime-v1.json) maps every
`supported` row to exact release-blocking checks. `Implemented / evidence
pending` is deliberately not a support claim.

The RC-supported scope includes:

- native and Pure-Go Linux/X11 within the documented XTEST/EWMH limits;
- advertised native wlroots/Sway protocols and the evidenced Hyprland
  active-window subset;
- consent-aware GNOME/KDE RemoteDesktop input, CGO/PipeWire persistent
  ScreenCast capture, Pure-Go one-shot Screenshot capture, and native
  CGO/Pure-Go multi-output logical bounds;
- consent-free macOS native/Pure-Go build, API, display metadata/scale, symbol
  resolution, and non-prompting permission/error contracts;
- native Windows default behavior and the Pure-Go Windows input, capture, and
  self-owned window/control contract.

The following macOS behavior is implemented but not in the RC-supported scope:

- Screen Recording-granted pixel capture;
- Accessibility-granted keyboard/pointer mutation;
- Accessibility-granted window inspection, activation, minimize/restore, and
  close, for both native and Pure-Go builds.

Those operations remain available and return explicit permission diagnostics.
They can be promoted only after
[LAB-69](https://linear.app/riotbox/issue/LAB-69/add-permission-granted-self-owned-macos-runtime-evidence)
passes on an isolated, self-owned remote macOS desktop. The RC does not ask
users or contributors to provide their workstation as test infrastructure.

## Migration guidance

Applications upgrading from beta.2 should:

1. Treat `GetRuntimeCapabilities` and `GetRuntimeDiagnostics` as runtime
   preflight, especially for permission- and compositor-dependent operations.
2. Prefer error-returning APIs so `ErrPermissionDenied`, `ErrNotSupported`, and
   backend failures cannot look like valid zero values.
3. Do not interpret “implemented” macOS permission-dependent APIs as
   release-qualified behavior; qualify them in the application's own managed
   environment or keep them disabled for the RC.
4. Keep portal consent explicit. RobotGo does not open RemoteDesktop or
   ScreenCast consent implicitly.
5. Re-run platform preflight after upgrades because desktop permissions,
   portal policy, compositor protocols, and XTEST/EWMH availability are runtime
   properties.

No migration step may persist screenshots, clipboard contents, typed text,
OCR input, window content, or permission tokens. Integration evidence must use
self-owned fixtures and remove all transient artifacts on success, failure,
timeout, and cancellation.

## Release evidence

The latest merged-main preparation baseline is proven on commit
`cd204c663e4ff5c8d33504d8cbf8b4dce1d8cc59` by
[`Release Evidence` run 30434061380](https://github.com/marang/robotgo/actions/runs/30434061380):
six native/Pure-Go snapshots, real GNOME/KDE multi-output portal input,
persistent ScreenCast and bounds, isolated Hyprland evidence, and all 29 exact
required checks passed. The run produced a checksum-bound evidence bundle.
The final merged release commit must pass a new exact manual run before the
annotated tag is created.

That qualification run cannot substitute for exact tag evidence. Publishing
the GitHub prerelease triggers the same workflow from `v1.0.0-rc.1`. The
workflow rejects any commit, tree, ref, matrix, check, or checksum mismatch and
attaches these immutable assets to the
[`v1.0.0-rc.1` release](https://github.com/marang/robotgo/releases/tag/v1.0.0-rc.1):

```text
robotgo-release-evidence-v1.0.0-rc.1-<commit>.tar.gz
robotgo-release-evidence-v1.0.0-rc.1-<commit>.tar.gz.sha256
```

Verify the downloaded archive before extracting it:

```bash
sha256sum -c robotgo-release-evidence-v1.0.0-rc.1-*.tar.gz.sha256
```

The release is no-go if either asset is absent, the checksum fails, the bundle
does not identify the annotated tag's peeled commit, any snapshot is missing,
or any of the 29 required checks is not successful.

## Qualification and rollback

The stable `v1.0.0` qualification window starts at the RC publication
timestamp and lasts at least seven full calendar days. Stable publication is
blocked by any unresolved critical/high regression, public API drift,
supported-platform evidence failure, privacy/cleanup regression, or mismatch
between source, tag, release, bundle, and checksum.

Published tags are immutable. If this RC is rejected, do not delete or move
`v1.0.0-rc.1`; record the no-go reason, fix the issue on `main`, and publish a
new incremented RC with fresh exact evidence. Consumers can roll back
reproducibly with:

```bash
go get github.com/marang/robotgo@v1.0.0-beta.2
```
